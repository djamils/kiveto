# Tech-Spec: Portal API v1 — corrected contract and slice 1 (foundation + invitation)

**Created:** 2026-10-29 — revised the same day after the adversarial review (findings F1–F16, see "Review amendments").

## Overview

### Problem Statement

The owner-facing mobile app (Flutter, iOS/Android — later the web Portal in Twig/Turbo) has no backend API. The draft contract `docs/frontend-theme/kiveto-mobile/Kiveto Portal — Contrat API v1.md` (git-ignored; moved to the versioned `openapi/portal-api-v1.md` by Task 1) was written ahead of the code and diverges from it on many points (names already taken, aggregates that do not exist, models that already exist elsewhere, formats), and the mockup `docs/frontend-theme/kiveto-mobile/Kiveto Portal mobile.html` (18 screens) exposes needs the contract does not cover. The existing `src/Presentation/Portal` is a two-controller Twig stub behind a session firewall; there is no API stack (no API Platform, no JWT, no refresh token, no problem+json, no idempotency, no cursor pagination), no OTP, no owner identity by phone, no client invitation to the Portal, and no account ↔ clinic client link.

### Solution

1. Rewrite the contract so it covers all 7 slices and is aligned with the codebase and the mockup, applying the decisions listed below.
2. Implement slice 1 on API Platform: API foundation, passwordless OTP authentication with JWT + home-made rotating refresh tokens, `User` of type `PORTAL`, clinic-initiated Portal invitation (accepted either through the link or through a plain phone login), `ClientLink`, `GET /me`, plus a minimal "Inviter au Portal" action on the clinic-side client sheet.
3. Update `CLAUDE.md` to state how API Platform operations satisfy the "one action per class" rule.

### Scope

**In Scope:**

- **Task 1 — contract rewrite** of the Portal API contract, moved to `openapi/portal-api-v1.md` (versioned, next to `openapi/portal.v1.yaml`), all 7 slices, applying every decision in "Technical Decisions" (code divergences + mockup gaps + review amendments).
- **API Platform foundation**: install/configure (JSON only, JSON-LD/Hydra off, `problem+json` errors, explicit route prefix `/api/portal/v1` + portal host, no recipe routes, docs disabled in prod), OpenAPI export committed to `openapi/portal.v1.yaml` with a CI check that fails on drift, stateless Bearer firewall for `/api/portal/v1`, `Idempotency-Key` support, cursor pagination helper, 404-not-403 tenant guard based on a confirmed `ClientLink`.
- **Auth**: `lexik/jwt-authentication-bundle` access token (15 min); home-made opaque refresh token (hashed, rotated on every use, single grace re-issue within 30 s, family revoked on reuse, ACTIVE check on every refresh, expires after 90 days of inactivity — D5); OTP challenge (code HMAC-hashed, 5 attempts, valid 10 min, resend availability) rate-limited with `symfony/rate-limiter` (3/h and 10/24 h per phone, 30/h per IP, 429 + `Retry-After`).
- **Endpoints** (no secret in any URL path — D27): `POST /auth/otp/request {phone}`, `POST /auth/otp/{challengeId}/resend {channel}`, `POST /auth/otp/verify`, `POST /invitations/lookup {token}`, `POST /invitations/otp {token}`, `POST /invitations/accept {token, challengeId, code, termsVersion}`, `POST /invitations/{invitationId}/accept {onboardingToken, termsVersion}`, `POST /auth/refresh`, `POST /auth/logout`, `GET /legal/terms/current`, `GET /me`.
- **Identity**: extend `User` with `UserType::PORTAL` — email and phone unique per `(type, value)`, add `phoneVerifiedAt`, no password (existing `UNUSABLE_PASSWORD_PREFIX` convention).
- **New `Context/ClientPortal`**: `PortalInvitation` aggregate (owns its own hashed token — no `TokenPurpose` involved), `ClientLink` (`pending` | `confirmed` | `revoked` internal; an accepted invitation creates it `confirmed` directly), owner profile (first name, last name, address — not on `User`).
- **Clinic side (minimal)**: "Inviter au Portal" button on the client sheet opening a confirmation dialog (phone/email prefilled, channel SMS or email); status shown on the sheet (non invité / invité le … / invitation expirée / actif / accès retiré); button becomes "Renvoyer l'invitation" / "Réinviter" (D16).
- **Portal host web**: minimal Twig landing page `/invitation` (store buttons, `Referrer-Policy: no-referrer`), `/.well-known/apple-app-site-association` and `/.well-known/assetlinks.json` so the link opens the app directly (D20).
- **CLAUDE.md**: API Platform operations (one Provider or one Processor per operation) satisfy the "one action per class" rule; the 3 file/`.ics` routes stay `__invoke` controllers.

**Out of Scope:**

- Slices 2 to 7 implementation (documents, pets & timeline, booking, consents & notifications, requests, organic arrival/listing) — only described in the corrected contract.
- `POST /auth/register` (free sign-up), email verification (`PATCH /me` with OTP), the email OTP channel (added to the `channel` enum once verified emails exist), listing pending invitations for an already logged-in user outside the OTP flow.
- Deferred deep linking (Firebase Dynamic Links no longer exists; not needed — D20).
- Push devices (`/me/devices`) and the push channel implementation.
- The Flutter repository.

### Technical Decisions

**Order and structure**
- Task 1 rewrites the contract (all 7 slices); subsequent tasks implement slice 1 against the corrected contract; CLAUDE.md is updated in this spec. Execution split in branches: D26.

**API stack**
- API Platform as the contract states. Resources are DTOs in `Presentation/Api/Portal/Resource`, never Doctrine entities; State Providers dispatch on the query bus, State Processors on the command bus. One operation = one Provider or one Processor = compliant with "one action per class"; it only translates HTTP ⇄ queries/commands, with no business logic, and a processor may chain a command then the session issuance (e.g. `VerifyPortalLoginOtp` then `IssuePortalSession`) or a lookup query then a command (round 3, R1). The 3 routes `…/documents/{id}/file`, `…/vaccination-booklet` (302) and `…/calendar.ics` (`text/calendar`) stay single-action `__invoke` controllers documented through an `OpenApiFactory` decorator.

**Authentication**
- JWT via `lexik/jwt-authentication-bundle` (no hand-written JWT).
- Refresh token is home-made: opaque, hashed, rotated on every use, family revocation — D5. No `gesdinet`.
- One input shape per route (no polymorphic DTO / `oneOf`) — D25.

**PORTAL user**
- Extend `User` with `UserType::PORTAL`. Email and phone uniqueness per `(type, value)` (a vet can own a pet). Add `phoneVerifiedAt`. No password — reuse `UNUSABLE_PASSWORD_PREFIX`. First name, last name and address live in the ClientPortal profile. The contract's `OwnerAccount` = a `User` of type PORTAL.

**Invitation / link**
- `PortalInvitation` in ClientPortal, owning its own hashed token (`AccountToken` requires an existing `userId`).
- Accepted invitation → `ClientLink` `confirmed` immediately. `pending` is only for link suggestions (slice 7).

**Naming (to avoid collisions)**
- `BookingMotif` with `durationMin` and `description`; `Context/ClinicListing`; new `Context/Document`; events keep code names (`AppointmentScheduled`, …).

**Consents (contract only, implementation slice 5)**
- Evolve `Client.communicationPreferences`; keep existing `ConsentKind` values (`appointment_reminders`, `vaccination_reminders`, `clinical_documents`, `billing`, `marketing`).
- Append-only history: kind, channel, granted/withdrawn, date, source (`portal` | `clinic`), author.
- Notification never reads consents; callers apply them.

**Other domain corrections (contract)**
- `weightGrams` integer; `sterilization` enum `intact` | `neutered` | `unknown`.
- Read models map reconciled patients → animals. Invoices carry `petIds[]` (possibly empty).
- Care items source = `PreventiveCareRecord.nextDueOn`.
- Renewal: whole prescription; `lineIds[]` removed; still a request validated by the clinic.

**Booking (contract, implementation slice 4)**
- `practitionerId` required; `GET /clinics/{c}/booking/practitioners?motifId=`; only bookable slots; real double-booking guarantee; `pending_clinic_confirmation` sends no SMS; Scheduling README rule D1 evolves in slice 4.

**Mockup gaps covered in the contract**
- Screen 6: `/me.clinics[]` adds `petNames[]`, `linkedAt`, `tags[]`. Screen 10: listing adds `phone`, `onlineBooking`, `tags[]`. Screen 11: new clients book through `/clinic-listings/{id}/booking/...`; that booking creates no `ClientLink` — what a new client sees of it before the link is confirmed is an open decision, settled in the slice-7 spec (R8). Screen 14: `POST /appointments` returns the full appointment; one input shape per route (D25): `POST /clinics/{c}/appointments {petId, …}` and `POST /clinics/{c}/appointments/with-new-pet {newPet, …}` (R7). Screen 15: `symptoms` enum `none` (exclusive), `cough`, `vomiting`, `diarrhea`, `appetite_loss`, `itching`, `lameness`. Screen 5: `certificate` document type.

**Decisions D1–D28**
- D1 — **PORTAL identity**: phone (E.164, `PhoneNumber` VO) is required and is the login identifier; `User::email(): ?string` — required for CLINIC/BACKOFFICE, optional for PORTAL; `User::requireEmail(): string` (throws when null) used by every staff path. **Creation invariants live in the named constructors only** (`register`, `invite`, `registerPortal`); `reconstitute()` checks nothing, so legacy rows (e.g. phone-less PORTAL rows set DISABLED by the migration) always load (F12). Uniqueness: unique index `(type, email)` (several NULLs allowed) + `(type, phone)` replace the global email index. **Every** email lookup becomes type-scoped: `findByEmail` and `findByEmailForUpdate` are removed from `UserRepositoryInterface` and replaced by `findByEmailAndType` / `findByEmailAndTypeForUpdate`; `addIfEmailFree` uses the `(type, email)` key. Callers: `AuthenticateUserHandler` (context type), `RegisterInvitedUserHandler` (CLINIC — staff invitations), `RequestPasswordResetHandler` (already CLINIC). - D4 — **OTP** (`OtpChallenge`, IdentityAccess, table `identity_access__otp_challenges`): 6-digit code, valid 10 min, 5 attempts per code, `resendAvailableAt` = +30 s, single use. **Code stored as `HMAC-SHA256(code, %kernel.secret%)`** through `OtpCodeHasherInterface` (an unsalted sha256 of 10⁶ values is reversible — F9). Purposes `login` and `invitation` (bound to an invitation id); a challenge of one purpose is never accepted by the routes of the other. Channel `sms` only in slice 1 (D18). - D5 — **Refresh tokens** (IdentityAccess, table `identity_access__refresh_tokens`, everything in DB): opaque 32-byte secret, only the sha256 is stored; columns `familyId`, `userId`, `rotatedAt`, `rotatedToId`, `graceSuccessorId`, `revokedAt`, `lastUsedAt`, `expiresAt`; 90 days of inactivity. Rotation loads the presented row `FOR UPDATE`. Rules, in order: (1) unknown/revoked/expired → result `revoked|expired|unknown`; (2) **user not ACTIVE PORTAL → revoke the family, result `user_inactive`**; (3) not yet rotated → rotate (`rotatedAt`, `rotatedToId`), new pair; (4) rotated < 30 s ago, successor unused **and `graceSuccessorId` null** → issue **one** new pair in the **same family**, set `graceSuccessorId`; (5) anything else (≥ 30 s, successor used, or a second grace replay) → revoke the whole family, `reuse_detected`. Since grace pairs share the family, any revocation revokes them too (F8). Logout: `RevokePortalSession(refreshToken, userId = JWT sub)` revokes the family only if it belongs to `sub`; otherwise no-op 204. The contract requires the mobile client to serialise refreshes (single in-flight refresh in the Dio interceptor); the grace window is a safety net.

- D29 — **Onboarding grant** (F6):
  - **Issuance, atomic** (F-D): inside `VerifyPortalLoginOtp`, in the transaction that consumes the challenge, the handler asks `PendingPortalInvitationsInterface::listForPhone(phone, now)`; when the list is non-empty and the account is not disabled, it calls `OtpChallenge::grantOnboarding(tokenHash, now)` (`onboarding_token_hash`, `onboarding_expires_at` = now + 15 min) and returns the clear token and the list in `LoginOtpOutcome`. There is **no `GrantOnboarding` command**: a grant can only be minted by verifying a code, at most once per challenge (`grantOnboarding` refuses a challenge that already carries one or that is not the one being consumed).
  - **Response**: `{status: "invitation_pending", onboardingToken, onboardingTokenExpiresAt, invitations: [{invitationId, clinic: {name, city}}]}` for a phone without account; for an ACTIVE user the `authenticated` body gains `pendingInvitations[]` + `onboardingToken` (empty list and null token otherwise). Expired or revoked invitations are never listed.
  - **Single owner of the check** (F-A): Presentation never resolves the grant. `POST /invitations/{invitationId}/accept {onboardingToken, termsVersion}` dispatches `AcceptPortalInvitationWithGrant`; ClientPortal checks terms, loads the invitation `FOR UPDATE` and calls `PortalIdentityInterface::claimIdentity` with the **clear** token, the invitation phone and id. `ClaimPortalIdentity` loads the challenge by `onboarding_token_hash` `FOR UPDATE`, checks it is neither expired nor revoked (`onboarding_invalid` → 401), compares the grant phone with the invitation phone (`phone_mismatch` → `404 invitation_invalid`), and only then finds or creates the user (D7). `ClaimPortalIdentity` never acts on a phone without a proof (code or grant) verified in the same transaction, so it cannot serve as a "user for any phone" primitive. No `ResolveOnboardingGrant` query exists.
  - **Scope**: the onboarding token is accepted **only** by `POST /invitations/{invitationId}/accept`. It is not a JWT and is never looked up by the `portal_api` firewall, `/auth/refresh`, `/auth/logout` or any other route; presented anywhere else (e.g. as `Authorization: Bearer`) it fails like any invalid credential (`401 unauthorized` / `refresh_revoked`).
  - **Phone binding, per invitation**: each acceptance compares the phone of **that** invitation with the grant phone; a grant from phone A can never accept an invitation of phone B (`404 invitation_invalid`, nothing written, grant untouched).
  - **Invalidation** (F-L): after each successful acceptance ClientPortal re-reads the phone's pending invitations with a locking read and, when none remains, calls `PortalIdentityInterface::revokeOnboardingGrants(phone)` (IdentityAccess `RevokeOnboardingGrantsForPhone`), which revokes **every** grant of that phone (several verifies may have produced several). Two concurrent last acceptances can each still see the other one pending, so **the guarantee is the use-time check**: when the targeted invitation is no longer pending (and the replay rule below does not apply), the outcome is `onboarding_invalid` if no pending invitation remains for the grant phone, `invitation_invalid` otherwise. Otherwise the grant expires after 15 min.
  - **Retry / replay** (F-C), both accept routes: if the targeted invitation is already `accepted` and `accepted_by_user_id` equals the ACTIVE user owning the proven phone (valid grant, or the same invitation challenge re-presented with the right code before its original expiry — D4 `already_verified`), the outcome is `accepted` again without any write and the processor issues a fresh session. `ClaimPortalIdentity` runs in a no-create mode for this check. Accepting the last pending invitation revokes the grant, so a grant replay after that answers `401 onboarding_invalid`; the contract tells the app to redo the phone login, which then returns `authenticated` — no extra mechanism (R3).
  - **Already-authenticated user** (F-N, documented, not coded): an ACTIVE user accepting through the grant receives a new token pair; the pair returned by `authenticated` stays valid and its family expires on its own.
