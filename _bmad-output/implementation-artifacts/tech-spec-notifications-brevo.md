# Tech-Spec: Notifications — e-mail, SMS and in-app through Brevo (appointments, billing, consultation documents, staff accounts)

**Created:** 2026-10-26

## Overview

### Problem Statement

Kiveto sends nothing today. `symfony/mailer` and `symfony/notifier` are installed but unused (`MAILER_DSN=null://null`, notifier stub). Consequences:

- Staff onboarding: the inviting administrator types a provisional password and hands it over by hand (`AddTeamMemberController`, « transmettez-lui son mot de passe provisoire »); there is no password reset.
- Clients receive no appointment confirmation, change, cancellation or reminder, although their consents per kind and channel are already recorded (`Client\Domain\ValueObject\Consent`, `ConsentKind`, `ContactChannel`).
- Invoices, unpaid reminders and consultation documents cannot be e-mailed; PDFs are only rendered on the fly in the Presentation layer.
- Staff have no in-app signal for events that concern them (new appointment booked by someone else, critical stock, lots about to expire).

The product owner provided the reference catalogue of notifications, with channels, triggers, wording and visual design: `docs/notifications/Notifications Kiveto.pdf` (13 sheets). This spec implements every sheet whose business prerequisite exists in the codebase.

### Solution

A new System bounded context `System/Notification`, built on the `System/ElectronicInvoicing` model (ports, integration events, architecture boundary test, env-selected adapters with a simulator), renders messages from **Twig templates owned by Kiveto** and sends them through **Brevo used as a plain transport** via the official Symfony bridges (`symfony/brevo-mailer` API transport for e-mail incl. attachments, `symfony/brevo-notifier` for SMS). It keeps a journal of every outbound message and updates its delivery status from **Brevo webhooks** received through the `symfony/webhook` component (Brevo mailer request parser + a Kiveto parser for SMS events). It also hosts the in-app notification feed (the « cloche »). Business BCs (Scheduling, Billing, Consultation, IdentityAccess, Inventory, Clinic) trigger notifications through Application commands and integration events; each business BC decides eligibility (consents, business re-checks) on its side.

### Scope

**In Scope:**

1. **`System/Notification` core**
   - `OutboundMessage` aggregate: channel (e-mail / SMS), purpose (notification kind), recipient (address or E.164 number + display name), clinic, optional client reference and business subject reference (appointment, invoice, consultation, user), rendered content frozen at send time (subject, HTML/text body or SMS text, attachment names), Brevo message id, status lifecycle `QUEUED → SENT → DELIVERED | BOUNCED | REJECTED | FAILED` (+ `SPAM`/`BLOCKED` mapped), status history.
   - Sending ports (e-mail, SMS) with adapters: Brevo (prod), Mailpit for e-mail in dev, a local simulator for SMS + webhook events (dev/test), selected by env var; simulator refused in prod.
   - Rendering of Twig templates (e-mail HTML + text, SMS text with GSM-7 / length check), shared e-mail layout reproducing the reference design (clinic header with logo/initial, detail table, primary button, footer with clinic coordinates, « Kiveto » header for account e-mails).
   - Integration event on each status change, consumed by Client to project the status into the client communication journal.
2. **Brevo webhooks**: public endpoint(s) outside the authenticated firewalls, authenticated (Brevo IP ranges behind correctly configured trusted proxies + shared secret, sent as a bearer header when Brevo supports it, else a masked `?token=`), idempotent, for e-mail events (via `symfony/brevo-mailer` request parser) and SMS events (Kiveto parser).
3. **Sender identity**
   - Client e-mails: `<Clinic name> <<clinic-slug>@mail.kiveto.fr>` (Kiveto sending sub-domain authenticated once in Brevo), Reply-To = clinic letterhead e-mail.
   - Staff account e-mails: `Kiveto <no-reply@kiveto.fr>`.
   - SMS sender: clinic short sender name (≤ 11 alphanumeric chars), set in clinic settings, default derived from the clinic name, fallback « Kiveto ».
4. **Appointments (Scheduling)** — sheets 1, 2, 3, 5
   - Confirmation after booking, change only when date, time or veterinarian changes, cancellation for an upcoming appointment only — each sent on **one channel**: the client's preferred channel when its address exists, else e-mail, else SMS (consent table: these messages are never blocked by a consent). The e-mail carries an `.ics` (invitation, update, cancellation). Sent through a 2-minute debounce (D2).
   - Reminder: SMS only, one per appointment, delay set in Paramètres › Agenda (24 h before, 48 h before, or same day at 8:00); scheduled scan every 15 min; appointment re-checked at send time (moved or cancelled → nothing sent); appointment booked too late for the delay → no reminder.
   - Scheduling publishes its domain events (scheduled, rescheduled, practitioner changed, cancelled) and reacts to them internally; no integration event is created (D1).
5. **Billing** — sheets 8, 9
   - « Envoyer » an issued invoice (single or bulk selection): e-mail with the invoice PDF attached, recorded in the invoice history; button disabled when the payer has no e-mail; variants « Reste dû » / « Réglée » (no payment link — see Out of Scope).
   - « Relancer » an invoice with a balance due (single or « Relancer tous les impayés »): SMS + e-mail on the accepted channels, PDF attached to the e-mail, each reminder traced on the invoice (« relancé 2 fois »).
   - Invoice / credit-note PDF generation moved out of the Presentation layer behind a port usable by the Application layer.
6. **Consultation** — sheet 10: from a closed consultation, the user ticks documents (report, prescription, invoice) and clicks « Envoyer par e-mail »; attachments are exactly the ticked PDFs; button disabled when the owner has no e-mail.
7. **Staff accounts (IdentityAccess)** — sheets 12, 13
   - Invitation: « Inviter un membre » in Équipe replaces the provisional password; member shown « Invité » until activation; single-use link expiring after 72 h; « Renvoyer » issues a new link and invalidates the previous one; the member chooses their password on activation.
   - Password reset: « Mot de passe oublié » on the **clinic** login screen (the link is hidden on the portal and backoffice hosts, which share the template — separate spec); same confirmation message and same response time whether the address exists or not; single-use link expiring after 30 min; every other session of the user is logged out after the reset.
8. **In-app bell (« cloche »)** — sheet 4, limited to the entries whose source exists: « Nouveau RDV » (to the appointment's veterinarian if they did not book it), « Stock critique » (Inventory stock alert), « Péremption proche » (scheduled, lots under the alert delay), plus « Quota SMS » (80 % / 100 % / overage cap reached, to clinic administrators); topbar bell with unread dot, dropdown with only non-empty filters (« Tout », « Activité » — no « Tâches » tab until tasks exist), « Tout marquer lu », click marks read and opens the target screen, 30-day history, « Voir tout l'historique » page.
9. **Client sheet**: every automated message appears in the existing `ClientCommunication` journal as an outbound entry with a delivery status badge (icon + label, readable without colour) updated by the webhooks; the client's appointment-reminder opt-out is visible and editable there.
10. **Clinic settings**: SMS sender name; reminder delay in Paramètres › Agenda; SMS usage « X / quota » (segments) for the current month with 80 % / 100 % banners; overage cap setting.
11. **SMS quota and overage** (pricing model « quota included, overage re-invoiced »)
    - Monthly quota = 400 segments × the **maximum number of active veterinarians during the calendar month**, pooled at clinic level. « Active » = effective VETERINARY membership whose user account is ACTIVE (invited, never-activated users do not count). The quota month is a Kiveto billing month and is always computed in Europe/Paris, whatever the clinic time zone. A month without any count row uses the last known count; the count is never below 1 (a quota of 0 never happens).
    - Usage counted from the Notification journal in **billed segments** (not messages), never from a separate counter: only SMS actually handed to the provider (`sent_at` set) count; QUEUED, BLOCKED_CAP and SMS failed before hand-over do not.
    - Beyond the quota sending continues; overage is counted at a configurable unit price (default 0.079 € HT / segment). Alpha: counted only, no automatic invoicing.
    - Banner at 80 % and 100 % in settings and in the bell for clinic administrators.
    - Overage cap per clinic (default 500 segments). The cap check counts sent **and queued** SMS segments and is serialised per clinic (lock), so a bulk send cannot jump over it. Once reached, **non-critical** SMS fall back to e-mail or are not sent and journaled « Bloqué (plafond) »: appointment reminder → e-mail only if the client's « Rappels de rendez-vous » consent allows e-mail and an e-mail exists; unpaid reminder → e-mail when an e-mail exists. **Critical** SMS (appointment confirmation, change, cancellation) still go out. Every SMS purpose is explicitly critical or non-critical. Lot recall (future spec) is never subject to quota or cap.
    - Bulk « Relancer tous les impayés » shows, before confirmation, the number of clients and the number of SMS segments it will consume.
12. **Dev environment**: Mailpit service enabled in `compose.override.yaml`; real Brevo usable in dev through `.env.local` (the product owner has a Brevo account).

**Out of Scope:**

- Sheets whose prerequisite does not exist yet (separate specs): payment-schedule reminder (sheet 6 — no instalments), cash-register closing reminder (sheet 7 — no cash closing / Z report), « Payer en ligne » links (sheets 8, 9 — no payment provider), lot recall (sheet 11 — dispensing does not record the lot per client/animal), bell entries « Résultat d'analyse reçu », « Tâche assignée », « Tâche terminée » (no tasks, no lab results), two-factor authentication mentioned in the invitation e-mail (no 2FA — sentence removed from the template).
- Vaccination reminders and marketing campaigns.
- Per-clinic sending domain (each clinic authenticating its own domain).
- Automatic invoicing of the SMS overage (counted only in alpha).
- Inbound messages (SMS replies, e-mail replies are handled by the clinic mailbox through Reply-To), WhatsApp.

### Technical Decisions

- Twig templates in Kiveto; Brevo is only a transport (`symfony/brevo-mailer` API transport, `symfony/brevo-notifier`); no Brevo-hosted templates.
- Delivery tracking through Brevo webhooks with `symfony/webhook` + `symfony/remote-event`.
- One spec, one branch (`feature/notifications-brevo`), delivered in ordered phases.
- Eligibility (consents, business re-checks) is decided by the business BC that requests the notification; `System/Notification` never reads another BC's data.
- Automated messages are logged in the existing client communication journal rather than in a separate block.
- **Consent rules** (legal basis: transactional messages rest on service execution, consent mainly governs prospecting — to be confirmed by legal counsel before production). A consent blocks only one message, the SMS appointment reminder; everywhere else it only chooses the channel:

  | Message | Rule | Client preference used |
  |---|---|---|
  | Appointment confirmation / change / cancellation | Always sent when an address exists, e-mail by default | None; channel follows the preferred channel when set |
  | Appointment reminder (SMS) | On by default, client can opt out | « Rappels de rendez-vous » |
  | Invoice / consultation documents | Explicit staff action, sent | Preferred channel (« Facturation » / « Documents cliniques ») |
  | Unpaid reminder | Sent, with bulk guardrails | « Facturation » channel |
  | Staff invitation / password reset | Always | None |
  | Lot recall (future spec) | Overrides everything, e-mail + SMS | None |

- **Request contract**: a single `RequestNotification` command (purpose, channel, resolved recipient, template + typed parameters, business subject reference, attachment references, optional e-mail fallback) with a mandatory **idempotency key**: one opaque string built by the requester (formats given per task), stored in a single column with a unique index, so a replayed command never sends twice. Criticality is not a parameter: it is fixed per purpose.
- **Attachments**: the requesting BC renders the PDF / `.ics` and stores it through the new `FileStorageInterface::storeAt(key, content)` under a **deterministic key** (a retry overwrites the same file, no orphans): `billing/sent/<invoice|credit-note>/<id>.pdf`, `notification/attachments/<idempotency key hash>/<filename>` for send-only files; binaries never travel in Messenger messages. Each attachment reference says who owns the file: `owner = REQUESTER` (e.g. Billing's stored invoice PDF — never touched by Notification) or `owner = NOTIFICATION` (files produced only for the send: `.ics`, consultation report and prescription PDFs rendered for the e-mail).
- **Reminders belong to Scheduling** (15-min scan, « reminder sent » state on its side, re-check at send time); Notification stays a dumb pipe.
- **Transactions, network and locks** (every command on `messenger.bus.command`, async or not, runs inside `doctrine_transaction`):
  - **Network first, writes last**: a handler that calls Gotenberg (PDF) does the rendering and the file write **before** any database write, so the open transaction holds no row lock during the network call; only the final inserts / updates and the `RequestNotification` dispatch take locks, for milliseconds.
  - **No Symfony Lock rows inside business transactions.** Serialisation uses InnoDB row locks taken with `SELECT … FOR UPDATE` inside the transaction and held until COMMIT (`innodb_lock_wait_timeout` → the message fails and Messenger retries it): the appointment notification state row (D2, created with `INSERT … ON DUPLICATE KEY UPDATE` first) and the clinic messaging profile row (SMS cap). A request that waits sees the committed rows of the previous one.
  - Each serialisation path has an integration test with two DBAL connections.
- **Client contact query**: Client exposes `GetClientNotificationContact(clientId)` returning available addresses, preferred channel and withdrawn consents; each calling BC reaches it through its own port + adapter and applies the consent table above.
- **PDF extraction first**: moving `DocumentPdfFactory` out of Presentation behind an Application port is phase 1 of the plan.
- **Unpaid-reminder guardrails**: confirmation with counts (clients, SMS segments), no second reminder of the same invoice on the same day, credit notes excluded.
- **GSM-7**: templates are pure GSM-7 (verified by tests); variable data (first name, last name, animal name, clinic name) is transliterated to GSM-7 (« Chloë » → « Chloe », « Côte » → « Cote »); segments computed at send time and stored on the message.
- **Status precedence**: webhook events may arrive out of order or twice; a final status is never overwritten by an intermediate one (same principle as ElectronicInvoicing F9). A soft bounce is never final (DEFERRED). Duplicate provider events are recognised by (status, occurredAt) and recorded once. An event for an external id not yet stored is kept in an unmatched-events table and replayed when the id is recorded.
- **Time**: appointment labels, reminder due times and the « booked too late » boundary use the **clinic time zone** (`Clinic::timeZone`, through `ClinicTimezoneResolverInterface`); a reminder « 24 h / 48 h avant » means the **same local wall-clock time** one / two days before (DST-safe). Only the SMS quota month is computed in Europe/Paris (Kiveto billing month). Purges and scans run on Europe/Paris schedules.
- **Veterinarian count for the quota**: maximum number of effective VETERINARY memberships whose user account is ACTIVE, over the calendar month (D6).
- **Retention (GDPR)**: frozen bodies (HTML, text, SMS text), recipient address / name and Notification-owned attachment files are purged **24 months** after sending; metadata (purpose, channel, status, dates, segments, subject reference) is kept for the quota and history. A purge never deletes a file whose owner is another BC (invoice PDFs stay with Billing). Brevo is declared as a sub-processor (DPA) before production — legal checklist item.
- **Disabled actions explain why** (tooltip: « Aucune adresse e-mail pour ce client »…); invitation states « Invité », « Invitation expirée » (+ « Renvoyer »), « Actif ».
- **Fixtures** (directive 7): messages in every status (delivered, bounced, rejected, blocked by cap), bell entries read and unread, invitations pending and expired, a clinic near its SMS quota.

**Decisions taken from the investigation (to confirm):**

- **D1 — Scheduling publishes its domain events, no integration events.** The schedule / reschedule / cancel handlers call `DomainEventPublisher::publish()` after save; subscribers **inside Scheduling** react (client messages, bell). No integration event is created since no other BC consumes them (same for Inventory's stock alert). `AppointmentScheduled` gains `ownerId` / `animalId` / `actorUserId`; commands gain an optional `actorUserId` set by the controllers from `SecurityUser::id()`.
- **D2 — One debounced sync per appointment.** Every appointment event schedules the same command `SyncAppointmentNotification(appointmentId)` 2 minutes later. The handler locks the appointment's notification state row (`SELECT … FOR UPDATE`, row created first if absent), compares the current appointment with the **last state actually notified** and derives the single message to send: confirmation, change, cancellation, or nothing. Concurrent or duplicate syncs therefore never send twice. The idempotency key is `appointment:<id>:<kind>:<n>` with `n` the notification counter incremented under the lock. A booking moved within the window gets one confirmation with the final slot; a booking cancelled within the window gets nothing; the agenda « Annuler » undo produces nothing.
- **D3 — Death of the animal.** `CancelAppointment` gains a `notifyClient` flag (default `true`); `DeclareAnimalDeathController` passes `false` — no « RDV annulé » message to a grieving owner.
- **D4 — `.ics`** generated by a small RFC 5545 writer in Scheduling Infrastructure (no new dependency): `METHOD:REQUEST` with a stable `UID` per appointment and an increasing `SEQUENCE` for confirmation / change, `METHOD:CANCEL` for cancellation.
- **D5 — PDF extraction.** New Shared Application port `DocumentPdfRendererInterface::render(template, context, footer)` (Twig + Gotenberg, Shared Infrastructure) with an Application exception; the logo data-URI moves to a Shared Twig runtime. Each BC owns its renderer behind an Application port: Billing (invoice with the billing context, credit note), Prescription (prescription), Consultation (report, with new ports for the patient / owner snapshot and practitioner, replacing `CockpitPatientBuilder` use). Presentation controllers call these renderers; the bundle and selection PDFs therefore get the missing billing context.
- **D6 — Vet count history.** **Clinic is the source of truth**: it records a daily snapshot `clinic__veterinarian_daily_counts(clinic_id, day, count)` (effective VETERINARY memberships whose user is ACTIVE — the ACTIVE status comes from an IdentityAccess query behind a Clinic port) through a scheduled task and on membership / activation changes, and pushes each value to Notification, which keeps a **read-only copy** (`notification__veterinarian_counts`) used by the quota. Quota = 400 × max over the month's rows; no row for the month → last known count; never below 1.
- **D7 — Client journal.** `ClientCommunication` gains `origin` (MANUAL | AUTOMATED), `deliveryStatus`, `notificationMessageId`, `statusChangedAt` and a `recordDeliveryStatus()` mutator allowed **only for automated entries**; manual entries stay immutable; README invariant amended. Client consumes Notification's status integration events (create on first event, update after). A batch query `GetClientsNotificationContacts(clinicId, clientIds[])` serves list screens (no N+1).
- **D8 — Contact query.** Client query `GetClientNotificationContact(clinicId, clientId)` → display name, civility, primary-or-first e-mail, primary mobile (E.164), preferred channel, consents by kind, archived flag. Scheduling, Billing and Consultation reach it through their own port + QueryBus adapter.
- **D9 — Reminder opt-out semantics.** The SMS reminder is sent when the client's `APPOINTMENT_REMINDERS` consent allows SMS. The client creation form pre-ticks it (« actif par défaut »); the client sheet lets the clinic switch it off. No back-fill of existing clients (alpha database is reset).
- **D10 — Invoice dispatch log.** Billing table `billing__invoice_dispatches` (invoice, kind SEND | REMINDER, channels, notification ids, author, at) feeds the invoice history (« Envoyée le… », « relancé 2 fois ») and the same-day reminder guard.
- **D11 — Accounts.** `User::invite()` (PENDING, no usable password), `activate(passwordHash)`, `changePassword(passwordHash)`; table `identity_access__account_tokens` (sha256 of the token, purpose INVITATION | PASSWORD_RESET, user, clinic_id for invitations, expiresAt, usedAt). An invitation token is scoped to **(clinic, user)**: a new invitation only invalidates the previous invitation of the same clinic, so two clinics inviting the same person never cancel each other. A new reset token invalidates the user's previous reset tokens. The onboarding user search includes PENDING clinic users (re-invite instead of colliding on the unique e-mail). Forgot-password rate limited per IP and per e-mail (sliding window) and processed asynchronously (constant response time). After a password reset every other session is logged out (password fingerprint in `SecurityUser`). README corrected.
- **D12 — Public routes and webhook.** Clinic host: `^/(mot-de-passe-oublie|reinitialiser/[^/]+|invitation/[^/]+)$` PUBLIC_ACCESS before the catch-all. Webhook routes are host-less (any host; production uses the public app host, e.g. `hooks.kiveto.fr` pointing to the same app). In dev, real Brevo webhooks reach the workstation through a tunnel (cloudflared quick tunnel → Nginx default server); since the tunnel hides Brevo's IP, `NOTIFICATION_WEBHOOK_SKIP_IP_CHECK=1` disables **only** the IP check (the secret stays mandatory) and is refused at boot when `APP_ENV=prod`. Both parsers are Kiveto classes (IP + secret check) that call the bridge's `BrevoPayloadConverter` directly — the bridge parser and its hard-coded IP list are not used. Webhooks: a stateless firewall `^/webhook/` (`security: false`) placed first, `symfony/webhook` controller with routing `brevo_mailer` (bridge parser) and `brevo_sms` (Kiveto parser), routes declared without host. Authentication: Brevo IP ranges (kept in a parameter, read through correctly configured `trusted_proxies`) **plus** a shared secret — sent by Brevo as an `Authorization: Bearer` header when its webhook settings allow it (verified at J1), otherwise as a `?token=` query parameter masked in Nginx and Symfony logs. The parsed remote events are consumed asynchronously (`ConsumeRemoteEventMessage` routed to `async`); out-of-order arrival is absorbed by the status precedence.
- **D13 — Bell sources.** « Nouveau RDV » from a Scheduling subscriber on `AppointmentScheduled` (to the practitioner when author ≠ practitioner); « Stock critique » posted by Inventory when the projector **inserts a new alert row** for OUT_OF_STOCK / LOW_STOCK CRITICAL, keyed by the alert row id and suppressed during a full re-projection (`DetectStockAlertsCommand`); « Péremption proche » from a daily Inventory scan of lots expiring within the existing 30-day INFO threshold, each lot notified **once** (per-lot record); « Quota SMS » from Notification (to clinic administrators). Recipients are VETERINARY_ASSISTANT members, or the clinic administrators when the clinic has none; resolved by the emitting side through a Clinic query.
- **D14 — Agenda settings.** The « Agenda » settings section (stub today) is implemented with the reminder delay; the SMS sender name and the SMS usage / overage cap live in a new « Notifications » settings section.
- **D15 — Staff display name.** A single Clinic query result field `printedName` (« Dr Claire Lambert », no dot) used by notifications; Presentation duplicates are left as they are.
