# Tech-Spec: Slice 1 — B2B electronic invoice transmission (ElectronicInvoicing core + Billing bridge, simulated platform)

**Created:** 2026-10-19

## Overview

### Problem Statement

Since slice 0 / 0.5, Kiveto qualifies a professional client (tax status, legal name, SIREN, French VAT number, registry + VIES verification), but it produces no electronic invoice and nothing transmits an issued B2B invoice to an Approved Platform (PA) or follows its lifecycle. Billing also lacks what an EN16931 / XP Z12-012 invoice needs: the `Payer` carries no SIREN / VAT / electronic address, invoice lines carry no goods/services category, there is no invoicing framework (BT-23), no invoice type code, no B2B payment terms / legal mentions, and nothing checks an invoice is transmissible before a sequential number is drawn. On the seller side, the clinic `Letterhead` holds a SIRET checked on length only and a free-text VAT number with no validation, while the CII requires the seller SIREN (BT-30) and VAT number (BT-31).

### Solution

A new, neutral bounded context `System/ElectronicInvoicing` (no PA concept, no veterinary concept) that renders the CII D22B invoice, validates it against the vendored XSD, submits it through ports modelled on XP Z12-013 semantics, polls lifecycle statuses (CDV / CDAR) and publishes an integration event — all PA interactions asynchronous, split network-only / record-only as in slice 0.5. Billing freezes a fiscal payer snapshot at issue, computes BT-23, checks local transmissibility before numbering, maps the invoice / credit note to a neutral transmission command through an anti-corruption adapter, and shows the transmission status (and « action requise ») on the invoice. In dev, demos and fixtures a `LocalPlatformSimulator` (no network) implements the same ports and plays deterministic scenarios chosen by the buyer SIREN.

### Scope

**In Scope:**

- `System/ElectronicInvoicing` (T1): aggregates `PlatformConnection` and `OutboundTransmission` (+ `LifecycleEvent`), platform ports `FlowSubmitter`, `FlowSearcher`, `FlowFetcher`, `DirectoryLookup`; technical ports (CII renderer, CDAR parser, document store); CII D22B rendering + XSD validation; tolerant CDAR parser; network/record command pairs (submit → record receipt; directory lookup before submission; sync → one record per flow, cursor advanced in its own record command) on `async_external` / `async_external_batch`; schedule (sync every 5 min, polling on `async_external_batch`); `LocalPlatformSimulator` + `electronic-invoicing:simulate` and `app:electronic-invoicing:connect --simulator <siren>` commands; guard forbidding the simulator in prod; tables `electronic_invoicing__platform_connections`, `__outbound_transmissions`, `__lifecycle_events`, `__simulated_flows`.
- Transmissions without a verified connection: created `Prepared`, waiting (badge « Plateforme non connectée »), released automatically when a connection becomes active (row-by-row `submission_requested_at` marker set on activation, then dispatch; the sync task also catches up orphaned `Prepared` transmissions). Issuing an invoice is never blocked by a missing connection.
- Directory lookup: part of the network step of the submission (no transaction). It only **corrects BT-49 at render time** when the directory returns another address than scheme `0225` + buyer SIREN; it **never holds the invoice back** — directory down or buyer unknown → keep scheme `0225` + buyer SIREN and submit anyway. ElectronicInvoicing records on the transmission the **electronic address actually used**; the transmitted file (kept with its sha256) is authoritative for what was sent, the Billing snapshot stays the value proposed at issue.
- `NON_TRANSMISE` (status 200 with that reason, buyer without a PA) is produced **only by the PA** (real or simulated — simulator scenario `000000000`), never fabricated by Kiveto.
- Billing (T1): `PayerSnapshot` frozen at issue (legal name, SIREN, VAT, BT-49 default scheme `0225` + buyer SIREN computed locally, BT-56 attention); `OperationCategory` per line (goods/services; mixed → `M` by default pending the accountant); `InvoicingFramework` (BT-23) + policy; `InvoiceTypeCode` 380 / 381 — credit notes (`CreditNote`) are transmitted too, with BT-25 reference to the original invoice; BT-153 = the line label (catalogue label, identical to the PDF — never the animal, a diagnosis or free notes); `PaymentTerms` + B2B legal mentions; `ElectronicInvoiceReadiness` — **local checks only** (buyer SIREN, legal name, address, BT-23 computable, B2B mentions, seller SIREN / VAT), run before the number is drawn; anti-corruption mapper and listeners; status badge and « action requise » in the UI.
- Amounts computed per VAT rate (see Technical Decisions): **B2B HT-first, strictly EN16931** (line net = qty × unit net rounded, VAT = base × rate rounded once — BR-CO-10 / 17 by construction); **B2C TTC-first** (exact TTC, base = TTC / (1 + rate), VAT = TTC − base, line nets by largest remainder); no BT-114; 6-decimal unit net price stored without float; Catalog stores the entered price and its mode (TTC / HT).
- Line categories: derived from the Taxation tax category of each line (frozen at creation); `AddManualInvoiceLine` requires a tax category (no UI in this slice; when the UI comes, the label field carries the hint « Pas de nom d'animal ni d'information médicale »); the global discount is a document-level allowance (BG-20) split per VAT rate. BT-23 is computed from lines only (document-level allowances / charges ignored).
- `Invoice::cancel()` forbidden for any issued B2B invoice (transmitted or not) — aggregate invariant, message « Une facture professionnelle émise ne s'annule pas : créez un avoir. » B2C cancellation unchanged (to be settled with the NF525 analysis).
- Transmission status stored on the Billing side as a read-only projection (a column fed by the integration-event listener); the invoice list never calls ElectronicInvoicing.
- Readiness failures at the counter show **what is missing**, in plain words, each with a direct link to fix it (client sheet, or clinic settings for seller data) — e.g. « SIREN du client manquant », « Adresse du client incomplète », « N° de TVA de la clinique invalide ». The link carries a return URL to the checkout in progress; the draft is kept (no number drawn).
- Clinic seller data: SIREN derived from the letterhead SIRET and VAT number validated with the shared `Siren` / `FrenchVatNumber` value objects (today: length-only SIRET, free-text VAT).
- Boundary: existing convention (no `PublicApi` namespace). ElectronicInvoicing exposes Application commands / queries and integration events; Billing reaches it through a port + adapter in `Billing/Infrastructure/Adapter/ElectronicInvoicing/`. Code outside ElectronicInvoicing may import from it **only** `Application\Command\…`, `Application\Query\…` and `Domain\Event\*IntegrationEvent` (the codebase places integration events in the publisher's `Domain/Event`, e.g. `Admission/Domain/Event/AdmissionClosedIntegrationEvent`); nothing else of its Domain or Infrastructure — enforced by an architecture test scoped to ElectronicInvoicing (Task 40).
- Standard UN/CEFACT CII D22B XSD (uncoupled, `docs/e-invoicing/CII_D22B/`) vendored into `Resources/xsd/cii-d22b` with a README (source, version); the PPF F1 XSDs are not used.

**Out of Scope:**

- T2: B2C e-reporting (Flux 10), clinic VAT regime / exigibility, `EReport`.
- T3: collection status 212, `PaymentVatAllocation`, CDAR rendering. **Reminder for T3: producing CDAR requires the UN/CEFACT CDAR XSD (not provided in `docs/e-invoicing`).**
- T4: real AFNOR XP Z12-013 adapter, OAuth2, Super PDP onboarding (`PlatformOnboarding`), sandbox / nightly CI, recorded sandbox fixtures.
- Directory lookup inside the readiness check (it would be a network call inside the issuing transaction).
- XSD validation of received CDAR (no CDAR XSD available; parser tolerant, tested on the AFNOR samples).
- Factur-X / PDF-A3 (the human-readable PDF stays the Gotenberg one).
- Corrective invoice 384, down payment 386, B2BInt, B2G.
- PA migration: no `Draining` / `Closed` connection status — not even the enum.
- **Receiving supplier invoices** (mandatory for every company since September 2026 — Procurement). After slice 1 the clinic is **not** fully compliant.
- Invoices issued before the deployment: no fiscal snapshot, never transmitted (alpha database is reset anyway).

### Technical Decisions

- Readiness is local only; BT-49 defaults to scheme `0225` + buyer SIREN (two fields, rendered as `schemeID="0225"`), frozen in the `PayerSnapshot`; directory lookup happens in ElectronicInvoicing, asynchronously, before submission.
- No PA connection never blocks issuing: the transmission waits in `Prepared` and is released when a connection becomes active.
- Existing BC boundary convention, guarded by an architecture test: outside ElectronicInvoicing only its `Application\Command\…`, `Application\Query\…` and `Domain\Event\*IntegrationEvent` may be imported.
- Mixed goods + services → framework `M` by default, pending the accountant's ruling (XP Z12-014 use case 31).
- Polling runs on `async_external_batch`.
- Directory lookup corrects BT-49 only, never blocks; `NON_TRANSMISE` comes only from the PA; the address actually used is recorded on the transmission.
- **Amount algorithm — two calculation modes, chosen by the processing rule** (replaces the per-line VAT of today):
  - **B2B → HT-first, strictly EN16931.** These are the only invoices validated by the platform. Unit net (BT-146, 6 decimals) = entered HT price, or entered TTC / (1 + rate); line net (BT-131) = round(qty × unit net); base per rate = Σ line nets − allowance; VAT per rate = round(base × rate) once. BR-CO-10 / 13 / 17 hold by construction and BT-131 = BT-129 × BT-146 (Peppol R120). A professional reasons in HT anyway, and the counter shows this recalculated total before payment: no surprise. (Measured during the review: with TTC-first, 16.7 % of totals at 20 % would break BR-CO-17 by one cent — hence HT-first for B2B.)
  - **B2C → TTC-first.** The client pays exactly the displayed price. Per rate: TTC = Σ line TTC (exact cents); base = round(TTC / (1 + rate)); VAT = TTC − base; line nets = base split by the **largest remainder method** (BR-CO-10). These invoices never leave as CII (T2 e-reporting sends daily totals per rate), so BR-CO-17 does not apply. Counter-example motivating it: 3 × 10,00 € TTC at 20 % computed HT-first gives 29,99 €.
  - **No BT-114** (rounding amount) in either mode: it is meant for cash rounding, not for hiding a calculation gap.
  - Catalog stores the **entered price and its mode** (TTC or HT) server-side; the JS conversion (`catalog.js:98`) disappears. Catalog joins B1a.
  - **No float anywhere**: the 6-decimal unit net price is an integer (micro-units) or an exact decimal. If `src/Shared/Money` (the project's Money module — there is no `System/Money`) has no value object at that scale, it is created there, not in Billing.
  - Amounts are frozen at issue; only drafts are recalculated.
  - Tests: 3 × 10,00 € in both modes (B2C 30,00 €; B2B 24,99 + 5,00 = 29,99 €), a typical veterinary basket in both modes with at least two Taxation-resolved rates, asserting exact TTC (B2C) and BR-CO-10 / 13 / 17 + R120 (B2B).
  - T2 reminder: a sale first reported as B2C and later invoiced to a professional (framework `S7`) is recalculated HT-first — possibly one cent off the receipt.
  - HT-entered lines in B2C are grossed up per unit to the cent; the global discount is applied per bucket (Task 2).
- A new professional at the counter needs a postal address (counter tab gains address fields, Task 13), otherwise readiness would always refuse it.
- ElectronicInvoicing takes the organisation SIREN as an argument of `connect` (it never reads Clinic); rendering, directory lookup and storage happen in the network step, the request handler only persists the neutral payload.
- **One `PlatformConnection` per SIREN (organisation)**, shared by every establishment (clinic) carrying it; one synchronisation per organisation. Invoice numbering is unique per SIREN (distinct prefixes per establishment, Task 16b), so `(seller SIREN, document number)` identifies a document for status resolution.
- **BT-153 = the line label** as on the PDF (catalogue / consultation label, e.g. « Consultation », « Vaccin CHPPiL », « Croquettes 10 kg »); Billing never adds the animal, a diagnosis or free notes to a line or to the CII. XP Z12-014 use case 36 (generic designation for professional secrecy) stays a question for the accountant / a lawyer, like framework `M`; not activated in T1.
- **CII validation: standard UN/CEFACT CII D22B XSD** (the PPF `F1_FULL` / `F1_BASE` XSDs are Flux 1 profiles and reject every AFNOR sample). The official D22B XSD (uncoupled publication, `docs/e-invoicing/CII_D22B/CII_D22B/XSD/uncoupled/Schema.zip`) is vendored in `src/System/ElectronicInvoicing/Infrastructure/Resources/xsd/cii-d22b/` with a README (source, version), and a test asserts the AFNOR UC1–UC5 CII samples pass it. EN16931 / BR-FR schematron deferred to T4 (sandbox; no `ext-xsl`, no XSLT 2 in PHP). Declare `ext-dom` / `ext-libxml` in composer.
- **Line category (goods / services) comes from the Taxation tax category**: `categories.yaml` carries the nature of each category (`veterinary.act.*` / `veterinary.service.*` → services; `veterinary.drug.*` / `veterinary.food.*` / `veterinary.consumable.*` → goods); Billing freezes it on the line at creation, like the rate. A line without a tax category (today: silent 0 % fallback) fails B2B readiness.
- **Manual lines: the Taxation tax category becomes a mandatory parameter of `AddManualInvoiceLine`** (no Acte/Produit enum); rate and nature are derived from it. No manual-line UI in this slice. `ADJUSTMENT` lines are created nowhere today: nothing to map; the global discount is a document-level allowance (BG-20) split per rate.
- Issued B2B invoices cannot be cancelled (credit note only).
- Transmission status = Billing read-only projection fed by the integration event.
- The transmission request leaves Billing **asynchronously through the outbox** (`ProfessionalDocumentIssuedIntegrationEvent` in the issuing transaction, then an async Billing consumer maps the frozen document and sends `RequestInvoiceTransmission`): issuing never depends on ElectronicInvoicing.
- Amounts are frozen at issue (lines, per-rate breakdown, totals); only drafts are recalculated.
- `ELECTRONIC_INVOICING_PLATFORM=disabled` is the production default until T4; the guard refuses only `simulator` in prod.
- At submission, seller SIREN (BT-30) must equal the connection's `organisationId`, otherwise `BLOCKED` / `ORGANISATION_MISMATCH`. Rendering / XSD failures are logged as errors (always our bug).
- Delivery as four stacked branches, lowest level first:
  - **B1a — Exact invoice amounts**: `UnitPrice`, largest-remainder allocation, TTC-first calculator, Taxation nature / designation, Catalog price mode, Consultation snapshot, recalculated and frozen lines (every invoice, B2C too).
  - **B1b — Billing fiscal model + Clinic seller data**: validated seller SIREN / VAT, buyer fiscal snapshot, BT-23, payment terms, `ElectronicInvoiceReadiness` + actionable counter errors, B2B `cancel()` invariant, counter address, PDF. Valuable on its own (complete B2B invoices without transmission).
  - **B2 — ElectronicInvoicing core + simulator**: tested end to end through its entry command, without Billing.
  - **B3 — Bridge + UI**: Billing outbox event + async consumer, mapper on frozen amounts, status projection, badge, « action requise », architecture test.
